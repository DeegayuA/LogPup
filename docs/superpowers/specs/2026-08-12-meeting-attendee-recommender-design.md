# Meeting Attendee Recommender — Design Spec (sub-project A)

Date: 2026-08-12
Status: approved in-session (sections 1–2 interactively; section 3 + delegated decisions under "do all tasks" mandate)
Suite: A (this spec) → B meeting-load reduction → C people KPIs → D soft deletes. **Build order: D, A, B, C** — D (app-wide soft deletes, separate spec) lands first; every delete path here inherits it.

## Goal

Reduce meeting count and size: recommend who is required / optional / can skip for every meeting, pre-fill the invite list while scheduling, audit past meetings, flag drifted recurring series, and give skippers a targeted recap so skipping is safe.

## User decisions (interactive)

- Surfaces: all four — scheduling, pre-meeting, retrospective, inferred series.
- Authority: advisory + pre-filled invite list; organizer edits freely.
- Series: inferred from history (pure function), no recurrence schema.
- `optional` is a real, visible invite property; propagates to Google Calendar and .ics.
- Skip payoff: auto recap targeted at non-attendees.
- Engine: hybrid — deterministic rules core; Gemini adds one bounded signal and may override a tier upward with cited evidence.
- Visibility: numeric score, full reason ledger, not-recommended list, AI-override detail, all retro output → **organizer + admins only**. Everyone else (including the person) sees tier + positive reasons, no numbers.
- Role floor: primary role/topic agenda match on someone assigned to the app ⇒ floored **required**.
- `tasks.updatedAt` ships in the same migration.

## Delegated decisions (flag to veto)

- Recap auto-release rides the existing daily 03:00 backup cron (≤24h delay); no extra cron.
- Decliners are EXCLUDED from the recap audience (deviation from the earlier draft rule; RSVPs are already public so exclusion leaks no tier signal; decliners keep full intel access on request).
- Name-guard-held recaps notify the organizer once at staging; held state stays visible in the Intelligence panel; no re-notification loop.
- Soft-delete rule (sub-project D) governs user-initiated deletes; the 180-day retro prune and recap-retraction notification deletes documented here are **privacy erasures and stay hard** — they exist to erase.

## Section 2 — Scoring model

### Signals (absolute 100-point ledger)

#### E1 — Open follow-ups the candidate owes (the spine of the model; HARD evidence)  — 30 max of 100

Per item: base = 12 if createdBy IS NOT NULL (a human wrote it), 6 if AI-derived; +2 if kind='action'. Recency multiplier on the SOURCE meeting's startsAt: <=14d x1.0, <=45d x0.75, <=120d x0.5, >120d x0.25. E1 = min(30, sum). RETROSPECTIVE SURFACE reconstructs as-of state: the predicate becomes (status='open' OR resolvedAt > meeting.startsAt), and an item with resolvedInMeetingId = this meeting scores x1.25 — being answered in the room is PROOF the person was needed, not a reason to score them zero. Orphan recovery (userId IS NULL): re-resolve personName in JS with matchPersonToAttendee (src/features/meetings/followups.ts:23-41), read-only, never written back; scored at 0.5x, and counts as hard evidence ONLY when the row is human-added AND the name is unambiguous within the source meeting's attendee list. The query runs with FULL visibility over meeting_followups — the caller-entitlement clause from fetchCarriedFollowups is NOT applied, or the score becomes a function of who opened the panel; instead the UI redacts, showing the organizer '2 open items from meetings you can't see' as a bare count.

- **Source:** meeting_followups (schema.ts:290-311): userId, personName, text, kind, status, createdBy, targetMeetingId, resolvedAt, resolvedInMeetingId, sourceMeetingId -> meetings.startsAt. No index on the table; batch with inArray over candidateIds.
- **Missing data:** No rows = 0 points, never a penalty. This family is ALWAYS available (needs no app, no recording, no board), which is why it carries the largest budget and why the required threshold is reachable on day one.

#### E1b — Follow-up PINNED to this meeting (targetMeetingId = meeting.id, status='open')  — 0 — hard override, not points

tier = 'required' unconditionally, bypassing thresholds, ceilings and the AI. targetMeetingId is only ever set by a human using the pin picker — it is a person saying in the UI 'they are needed HERE'. Reason carries the followup id and the name of whoever pinned it.

- **Source:** meeting_followups.targetMeetingId (schema.ts:305-307), .status, .userId, .createdBy
- **Missing data:** Almost always absent. Absence changes nothing.

#### E2 — Open tasks assigned to the candidate in the meeting's app (HARD evidence)  — 20 max

One grouped query, covered by tasks_app_sprint_sort_idx on its app_id prefix. openPts = 4 per open task, cap 12. inProgressPts = +2 each, cap 4. sprintBonus = +4 FLAT (not per task) if >=1 open task sits in the running sprint, where 'running' = status='active' OR (status='planned' AND startDate <= today AND endDate >= today), today = toIsoDateInTimeZone(new Date(), LK_TIMEZONE), winner = soonest endDate, additionally guarded endDate >= today because sprints never auto-close. Cap 20. STRICTLY POSITIVE-ONLY: zero tasks contributes exactly 0 and can never subtract — a designer, QA engineer, PM or new hire legitimately has no board rows. No board-coverage gate is needed because there is no denominator to distort: an unused board simply awards nobody anything. RETROSPECTIVE SURFACE adds tasks.createdAt <= meeting.startsAt so the meeting is never judged on work it itself created; open-at-the-time is genuinely underivable (no tasks.updatedAt), so the retro reason is worded 'owned N tasks in Vela created before this meeting' and the family is capped at 10 there.

- **Source:** tasks.appId/.status/.assigneeId/.sprintId/.createdAt (schema.ts:154-185), sprints.status/.startDate/.endDate (schema.ts:143-152)
- **Missing data:** meeting.appId null and not inferrable -> family UNAVAILABLE, 0 for everyone, no renormalisation (absolute ledger). Zero tasks -> 0, never negative. tasks.assigneeId is not constrained to app membership, so someone with tasks but no assignments row is scored, not dropped.

#### E3 — Deterministic role <-> agenda/title topic match (HARD evidence, and the one signal that can floor a person to required)  — 14 max

A pure TOPIC_BUCKETS table in src/lib/agenda-topics.ts with a sibling .test.ts: { keywords[], primaryRoles[], adjacentRoles[] }, roles quoted verbatim from JOB_ROLE_GROUPS (src/lib/job-roles.ts:15-112). Match = case-insensitive whole-word hit of a bucket keyword in `${title} ${agenda ?? ''}`. Candidate role tokens = [users.title, assignments.role for this app]. Primary hit 14, adjacent 7, apps.techTags overlap with no role hit 3, no hit 0. Best single bucket only; buckets do not stack. LINT TEST, mandatory: every value in JOB_ROLES must appear in at least one bucket's primaryRoles or adjacentRoles — an 8-bucket table over a ~70-role vocabulary silently zeroes Support, Finance, HR, Marketing and every generalist engineer, and a structural 0 is indistinguishable in the UI from 'we checked'. Until the lint passes, a role that matches no bucket is UNKNOWN and the family contributes 0 with the caveat line shown. REQUIRED FLOOR: a PRIMARY hit on a candidate who is also assigned to the meeting's app -> tier floored at 'required'. That is the deterministic answer to 'the designer is optional at her own design review', it cites a verbatim agenda span and a verbatim role string, and it is exactly as auditable as every other reason.

- **Source:** users.title (schema.ts:31), assignments.role (schema.ts:77), apps.techTags, meetings.title/.agenda (schema.ts:190,193)
- **Missing data:** agenda null AND title tokenizes to <3 non-stopword words -> 0 for everyone, no penalty, caveat line shown. Role strings are free text with no enum; a miss is 'unknown', never a subtraction.

#### E4 — Named with discussion POINTS in past AI notes of the series  — 10 max

Read meeting_ai_notes.perPerson jsonb over series meetings within 180 days. Resolve each entry's free-text name in JS via matchPersonToAttendee (never SQL name equality — SQL diverges from the 'unique first-name match only' rule). Count entry.points ONLY, capped at 3 per meeting, x2 pts, x recency (1.0 <=30d / 0.7 <=90d / 0.4 <=180d), cap 10. actionItems are deliberately excluded: deriveAndInsertFollowups materialises exactly those as meeting_followups rows already scored in E1, and one artifact must not fund two families. Entries with no `name`, or whose name matches /^speaker \d+$/i, are skipped and counted in a diagnostic.

- **Source:** meeting_ai_notes.perPerson jsonb (schema.ts:221 shape [{name, points[], actionItems[]}])
- **Missing data:** No meeting_ai_notes row, or no resolvable name -> 0, no penalty. This is the only place `points` (what a person actually said or decided) is materialised anywhere in the schema, which is why it survives YAGNI despite being unvalidated model output.

#### E5 — Voice participation in past occurrences of the series. POSITIVE-ONLY. No negative branch exists.  — 8 max

TURN COUNT, not char_length. The transcription prompt (ai-actions.ts:577-591) treats Sinhala/English code-switching as the common case, and Sinhala renders the same utterance in ~25-30% fewer characters — a char-based share measures script density and systematically under-credits whoever speaks less English. Turn count is script-independent and measures 'took part', not 'talked most'. PER-CANDIDATE GATE (not per-meeting): a past meeting counts for a candidate ONLY if a meeting_speakers row maps some label to that userId for that meetingId, OR >=1 meeting_note_segments row for that meeting has speakerId = that user. An unmapped 'Speaker 3' is UNKNOWN — the meeting is simply UNAVAILABLE for that person, contributing nothing rather than a zero. resolvedTurnShare = their turns / turns with a resolved speakerId; expected = 1/resolvedSpeakerCount; ratio >=0.75 -> 8, >=0.35 -> 4, else 2. Averaged over kept meetings with recency decay. Needs a new index on meeting_note_segments.meetingId (the table declares none, schema.ts:361-371) before this ships.

- **Source:** meeting_note_segments.source='voice'/.speakerId/.speakerLabel (schema.ts:361-371), meeting_speakers (schema.ts:377-386)
- **Missing data:** Unresolved speaker, no recording, or no meeting_speakers mapping -> UNAVAILABLE for that candidate, 0 points, NO penalty and no tier cap. There is no 'they were silent' inference anywhere in this model: attribution failure, medical leave, parental leave, the Avurudu shutdown and genuine quietness are indistinguishable in this schema (there is no absence table), and the two-Kasuns case — matchPersonToAttendee deliberately returns null on an ambiguous first name — makes the studio's most common names the least resolvable.

#### E6 — Ownership: app lead + allocation to the app. Deliberately starved.  — 12 max

apps.leadId = candidate -> 8 pts + floor 'optional' (NOT required: leadership buys a seat, not a summons; a lead with three open follow-ups reaches required on the follow-ups, which is the point). Allocation BANDS on this app, not a continuous curve: 1-24% -> 2, 25-49% -> 3, >=50% -> 4. Bands exist because allocationPct is an admin-typed integer with min 5 and a continuous curve let one percentage point decide whether a person got an invite at all. Any non-zero allocation -> floor 'optional'. When apps.leadId IS NULL, an assignments.role in a small allowlist drawn verbatim from JOB_ROLE_GROUPS ('Tech Lead','Engineering Manager','Product Owner','Project Manager','Scrum Master','Delivery Manager','CTO', …) -> 3 pts, tagged heuristic:true, no floor. Never a /lead/i regex. Cap 12. Query = getTeamForApp's read PLUS the users.active/status='approved' filter it is missing.

- **Source:** assignments.userId/.appId/.role/.allocationPct (schema.ts:73-79, uniqueIndex assignments_user_app_idx), apps.leadId (schema.ts:69)
- **Missing data:** No assignments row = 'not on the app' = 0, never NULL. apps.leadId is nullable and independent of assignments, so a leadId hit ADDS the candidate to the pool at 0% allocation rather than only re-ranking. Both sources can hand you a deactivated user — the eligibility gate is applied on top. Ownership at its maximum (12) is exactly the optional threshold and 18 points short of required: admin-typed facts about a person can never, alone, make them required.

#### E7 — Attendance habit across the inferred series  — 6 max

attendedRatio over the last 6 occurrences within 180d: >=0.8 -> 6, >=0.5 -> 4, >=0.25 -> 2, else 0. NEVER counts as hard evidence, and 6 points cannot reach the 30-point required threshold under any combination lacking hard evidence — so 'habit alone is never required' needs no special case, the arithmetic enforces it.

- **Source:** meeting_attendees (meetingId,userId) (schema.ts:202-207) joined to meetings.startsAt over the series key
- **Missing data:** Fewer than 2 prior occurrences -> family UNAVAILABLE, 0, no penalty. Note this is the model's one self-reinforcing loop (recommendations create attendance creates habit points); it is capped at 6/100 and barred from required so the loop is slow enough to observe in the accepted/dismissed rates before it matters.

#### A1 — Gemini agenda-topic relevance (the AI scoring component)  — 10 max — 10% of the ledger, and it can never make anyone required by points

score 0|1|2 x 5. Runs ONLY when meetings.agenda is non-empty after trim AND tokenizes to >=3 non-stopword words; otherwise the model is not called at all. Prompt carries opaque candidate ids (c1..cN) — never names, never emails — plus per candidate <=8 open task TITLES (never descriptions), <=4 open follow-up texts, and their users.title / assignments.role strings. callGemini(organizerId, parts, { responseJson: true }). Expected: { relevance: [{ id, score, agendaQuote, evidenceQuote, evidenceId }] }. FIVE VALIDATIONS before any point is credited, all in a pure module with a sibling .test.ts: (1) id in the issued set; (2) score clamped to integer 0..2; (3) agendaQuote a verbatim >=12-char case-insensitive substring of meetings.agenda; (4) evidenceQuote a verbatim substring of THAT candidate's own packet — task title, follow-up text, users.title, OR assignments.role; (5) evidenceId in the issued id set, or null when the anchor is the role string. Any failure -> that entry scores 0 and the raw entry is logged. Validation (4) explicitly admits the role string as an anchor: requiring a task or follow-up anchor makes the AI a pure multiplier on people who already have artifacts, and structurally zeroes the designer who made the mockups the agenda is about. BOUNDING RULE: A1 counts toward the optional threshold but the required threshold is evaluated on DETERMINISTIC points only, so a perfect A1 with nothing behind it totals 10 — below the 12-point optional line. The AI can sharpen a case; it cannot create one. INJECTION POSTURE: agenda text and task titles are user-authored and are passed as delimited data, never interpolated into instructions; the model's total expressible effect on the world is <=10 points and <=2 one-step upward promotions, both shown to the organizer with their quotes.

- **Source:** meetings.agenda/.title, tasks.title, meeting_followups.text, users.title, assignments.role; src/features/gemini/client.ts:185
- **Missing data:** No agenda, no gemini_keys row, quota exhausted, GeminiError, or 8s timeout -> A1 = 0 for everyone, reason code ai_unavailable stored, deterministic recommendation ships unchanged. Thresholds are absolute and do NOT move, so an AI outage makes the model slightly more conservative rather than silently re-scaling everyone. Result cached on the row per (meetingId, sha256(agenda), sha256(poolIds)) so reopening the panel never re-rolls a score.

#### GATE — Eligibility (not points)  — 0 — hard pre-scoring gate

Forward-looking surfaces (scheduling, pre-meeting, series): and(eq(users.active,true), eq(users.status,'approved')), the canonical filter from listActiveUsers/getUserCapacities, applied BEFORE scoring. A 'pending' user is blocked from every route but /pending by the proxy — inviting them produces a calendar invite to someone who cannot open the app. RETROSPECTIVE surface: NOT applied to anyone holding a meeting_attendees row for that meeting — they were demonstrably there, and filtering them makes the analysis lie about who was in the room.

- **Source:** users.active (schema.ts:43), users.status (schema.ts:48)
- **Missing data:** getTeamForApp and the apps.leadId read do not apply this filter today (the admin UI even renders a 'Current lead — deactivated' case), so it must be added explicitly on top of E6's query or the recommender inherits the bug.

#### GATE — Candidate pool (not points)  — 0 — decides who can be scored at all

pool = eligible assignments on meeting.appId UNION apps.leadId UNION anyone with an open follow-up from this app's meetings UNION anyone with open tasks in this app UNION attendees of the last 6 series occurrences UNION meeting.createdBy UNION anyone who used the 'Ask to be included' opt-in on this series. RETROSPECTIVE surface additionally unions the meeting's ACTUAL meeting_attendees rows — a retrospective whose pool is the invite list can only ever confirm the organizer's original mistake, and the finding it exists to produce ('Priya owned the failing suite, had two open items, and was not invited') is unreachable without this union. Retro output is rendered as two organizer-private lists: 'invited, could have been optional' and 'not invited, had evidence'.

- **Source:** assignments, apps.leadId, meeting_followups, tasks, meeting_attendees, meetings.createdBy
- **Missing data:** A roster-wide pool is deliberately NOT used: under an absolute ledger it produces a long tail of zero-point rows, which is noise dressed as a ranking. You are a candidate because something in the database points at you.

#### FLAG — Real calendar conflict (organizer-facing only, not a score term and not a tier change)  — 0 — displayed flag

Overlap query over meetings joined to meeting_attendees for the candidate: other.startsAt < meeting.endsAt AND other.endsAt > meeting.startsAt, excluding this meeting. Rendered to the organizer as 'Already on "Client demo — Orbit", 14:00-15:00'. It does NOT cap or lower the tier: a double-booking is a scheduling fact the organizer resolves, not evidence that the person is unnecessary, and demoting on it would make the model punish popular people.

- **Source:** meetings.startsAt/.endsAt (schema.ts:189-190) x meeting_attendees; note meeting_attendees' PK is (meetingId,userId) so by-userId lookups are unindexed — fine at studio scale
- **Missing data:** No overlap -> no flag. This is the only genuine availability signal in the schema; allocationPct is a workload share, not a calendar.

### Tiering

ABSOLUTE POINT LEDGER, FIXED THRESHOLDS, NO DIVISION ANYWHERE. Deterministic families E1..E7 sum to a maximum of 90 (30+20+14+10+8+12+6); A1 adds up to 10; total maximum 100. There is no normalized denominator and no dynamic cut, because every normalized design in the candidate set divided by a denominator that can legitimately be zero (no app + no agenda + no series = NaN, and `NaN >= 30` is false, so every candidate silently fell to `skip`, which means no meeting_attendees row, which means no invite and no notification). Zero points here means zero evidence, not 'lowest ranked'.

TWO MODES.
ABSTAIN MODE fires when fewer than 2 distinct candidates carry >=1 hard-evidence item (hard evidence = an E1 item with a resolved userId or a qualifying human-added name match, an E2 open task row, an E3 primary role/topic hit, or E1b). One stray AI-guessed follow-up must not flip the product from honest to confident. In abstain mode NO tiers are computed and no negative statement is made about anyone: the organizer is pre-filled required, every eligible person assigned to the app is pre-filled OPTIONAL, and the panel says "Not enough to go on yet — LogPup has no open follow-ups, no tasks in Vela and no diarized recording of this series. Everyone on Vela is pre-filled as optional; trim it yourself." With no app it pre-fills the organizer plus a clearly-unscored button "Add the attendees of the last 'Monday client sync' (5 people)". This is the honest day-one output and, on today's data, the modal one.

SCORING MODE pipeline, in this exact order:
R1. points_det = sum of E1..E7, each capped at its family cap (max 90). points_total = points_det + A1 (max 100).
R2. required if points_det >= 30 AND hardEvidence >= 1. The required test uses DETERMINISTIC points only — the AI's 10 points cannot carry anyone over the line by arithmetic.
R3. else optional if points_total >= 12.
R4. else skip.
R5. FLOORS (minimum tier optional, applied after R2-R4): any non-zero allocation on the meeting's app; apps.leadId; hardEvidence >= 1; users.createdAt or the (userId, appId) assignment within 21 days ("new — not enough history to judge", and all history-based families reported as unavailable rather than zero); an existing meeting_attendees row a human created; an attendee of the immediately previous occurrence of the series; a self opt-in ("Ask to be included" — a person-controlled control that writes the row and floors the series, and outranks the model); RETURNER GUARD — a candidate with zero meeting_attendees 'going' rows, zero tasks.createdAt and zero authored segments across a contiguous >=21-day stretch inside the lookback window has that stretch marked UNAVAILABLE for E4/E5/E7 rather than counted, and is floored optional for one full series cycle after reappearing.
R6. REQUIRED FLOOR: E3 primary role/topic hit AND assigned to the meeting's app -> required.
R7. HARD OVERRIDES, beating everything above: meeting.createdBy -> required, always, every surface. Open follow-up with targetMeetingId = this meeting -> required.
R8. CEILING: when meeting.appId is null and no app could be inferred, nobody may be required except the organizer, a pinned-followup holder, or a series regular with attendedRatio >= 0.75 over >= 3 prior occurrences.
R9. AI override, last, within ai_override_bounds.
R10. SOFT CAP: if more than 8 people land in required, show the organizer a warning with the ranked list. No automatic demotion — a machine-imposed quota that publicly demotes the person the studio depends on most is worse than a long invite.

CONSEQUENCE OF R5, STATED PLAINLY: `skip` is rare by construction. Anyone assigned to the meeting's app is at least optional. `skip` applies to people pulled into the pool by a stale attendance record or by tasks in an app they are not on, and it is never the default outcome for a team member. This is deliberate: `skip` is implemented as the ABSENCE of a row, so a wrong skip is invisible in the invite, unrecoverable, and the person is never told the meeting exists. The feature's sharp end is required-vs-optional and the fact that optional is real; it is not silent exclusion. On the scheduling and pre-meeting surfaces the recommender may never remove someone who was on the previous occurrence of the series — it demotes them to optional and shows the organizer an explicit "remove" action a human has to click.

WHAT THE TIERS WRITE: required -> meeting_attendees row with optional:false. optional -> row with optional:true. skip -> no row, but the candidate still renders in the ORGANIZER's panel under "not recommended" with their reason, so exclusions are auditable to the one person who can act on them.

VISIBILITY (enforced in the query, not the component — getMeetingsForApp filters on appId alone today, so every meeting on an app is readable by everyone on it). The numeric score, the full reason ledger, the "not recommended" list, the conflict flag and all retrospective output are visible ONLY to meeting.createdBy and admins. Every other viewer, including the person themselves, sees tiers and positive reasons only, and NO number. A machine-authored, dated, stack-ranked statement about a named colleague, published on a page all nine people can open, will be screenshotted; a 0-100 score beside a person's name reads as a rating of a human no matter how it is framed.

SURFACE-SPECIFIC RULES. ### Series rule

ONE pure function, `seriesKey(title: string): string | null`, in src/features/meetings/attendee-series.ts with a sibling .test.ts. It is the SINGLE normaliser — the recommender, the series surface and the no-app inference ladder all call it; a second ad-hoc lower/trim is how the halves silently disagree and every retrospective reason becomes unverifiable.

Steps, in order: (1) NFKC normalise, lowercase, (2) strip a trailing parenthetical /\s*\([^)]*\)\s*$/, (3) delete weekday names (mon/monday/tue/... plus සඳුදා-family tokens), month names, ordinals (1st/2nd/3rd), date-like tokens (\d{1,4}[-/.]\d{1,2}([-/.]\d{1,4})?), clock times (\d{1,2}(:\d{2})?\s*(am|pm)), and issue/sprint/week numbers (#\d+, w\d+, sprint \d+), (4) delete cadence words only — daily, weekly, biweekly, fortnightly, monthly, bi-weekly — never content words like "sync" or "standup", (5) collapse all non-alphanumeric runs to single spaces and trim. Return null if the result is under 3 characters or has zero non-stopword tokens.

Two meetings are the same SERIES when seriesKey is non-null and equal AND appId is equal (both null counts as equal). The window is the most recent 6 occurrences with startsAt < target.startsAt and within 180 days. A series is ESTABLISHED at >= 2 occurrences; below that, E4, E5 and E7 are UNAVAILABLE (0 points, no penalty, caveat line shown). This collapses "Standup", "Daily standup" and "Standup (Tue)" into one series and keeps "Vela standup" and "Orbit standup" apart via appId.

Perf: `meetings` has no index on appId, title or startsAt, so these scans are seq-scans. Acceptable at studio volume; batch with inArray over meeting ids and group in JS the way attachAttendees already does, never loop per candidate. Add index(appId, startsAt) the first time meeting volume hurts.

### AI component (A1)

A1, AGENDA-TOPIC RELEVANCE — 10 of 100 points, and structurally incapable of producing hard evidence or, by arithmetic, a `required` tier.

Runs only when meetings.agenda is non-empty after trim and tokenizes to >= 3 non-stopword words. A four-word title carries no topic and calling the model on it only manufactures relevance and burns the per-user Gemini key quota.

Sees: the agenda and title, plus, per candidate, an opaque id (c1..cN) — never a name, never an email — up to 8 open task TITLES (never descriptions: descriptions are a bigger, less curated surface and titles are already exposed to every signed-in user by search), up to 4 open follow-up texts, and their users.title / assignments.role strings. That caps the prompt at roughly 12 short strings per person.

Called through callGemini(organizerId, parts, { responseJson: true }) (src/features/gemini/client.ts:185), which already owns key rotation, model fallback and retry. Expected shape { relevance: [{ id, score: 0|1|2, agendaQuote, evidenceQuote, evidenceId }] }; points = score x 5.

Five validations, in a pure module with a sibling .test.ts, before any point is credited: id in the issued set (the filterValidIds discipline — the model selects from a list, it never invents ids); score clamped to integer 0..2; agendaQuote a verbatim >=12-character case-insensitive substring of meetings.agenda; evidenceQuote a verbatim substring of THAT candidate's own packet, where the packet explicitly includes their users.title and assignments.role as well as their task titles and follow-up texts; evidenceId in the issued task/follow-up id set, or null when the anchor is the role string. Any failure zeroes that entry and logs the raw output. There is no partial credit and no retry.

Deterministic: computed once per (meetingId, sha256(agenda), sha256(sorted pool ids)) and cached on the row. Reopening the panel never re-rolls a score; editing the agenda is the only thing that invalidates the cache.

Failure is total and silent to the score: no key, quota exhausted, GeminiError, or 8s timeout -> A1 = 0 for everyone, reason ai_unavailable, thresholds unchanged (they are absolute, so an outage makes the model more conservative rather than re-scaling everyone), and the deterministic recommendation ships complete. Gemini is never on the critical path.

Bounding property worth stating out loud: a candidate whose only score is a perfect A1 totals 10, which is below the 12-point optional line, and the required test ignores A1 entirely. The model can reorder the middle of the list; it cannot invent an attendee out of a plausible sentence.

### AI override bounds

MAY DO, and only this: move exactly ONE tier step, UPWARD ONLY — skip -> optional, or optional -> required. At most 2 override proposals per run; if more are returned, keep the 2 with the highest validated A1 score and log the discards. optional -> required additionally requires the candidate's deterministic points >= 18; skip -> optional requires >= 6. No structural stake, no promotion — this is the rule that stops the model turning the recommender into a keyword-search invite blaster.

MAY NEVER DO:
- Demote. required -> optional and optional -> skip are structurally unavailable, discarded rather than clamped. A demotion argues against a human-observed artifact, and a wrong demotion is silent: the person simply never gets the invite. This model has no demotion path at all — there are no negative terms anywhere in the ledger.
- Two steps (skip -> required).
- Override the organizer, a pinned-followup required, a candidate at any floor from R5/R6, or anyone already deterministically required.
- Run when the agenda is empty, when Gemini is unavailable, or on the retrospective surface.
- Touch the deterministic score or the reasons array. It writes ONLY the final tier; scoreDet and reasons keep their deterministic values, so the row always answers "what would the rules alone have said?".
- See any person's name or email. The packet is opaque ids.

MUST CITE, all validated in code before the override applies: agendaQuote (verbatim >=12-char case-insensitive substring of meetings.agenda), evidenceQuote (verbatim substring of that candidate's own packet, including their role string), evidenceId (whitelisted uuid, or null when the anchor is the role string), and basis from a closed enum: 'agenda_names_their_work' | 'agenda_topic_matches_their_role'. Any failure discards the whole override — no partial acceptance — and writes it to aiOverrideRejected so the failure mode is inspectable rather than invisible.

UNTRUSTED TEXT: agenda text and task titles are written by users, and task titles in particular are candidate-controlled. They are passed as delimited data, never interpolated into the instruction block, and the output schema is closed. The residual gaming surface is bounded to <= 10 points and <= 2 one-step upward promotions per meeting, each rendered to the organizer with both quotes and a one-click undo.

STORED AND SHOWN: aiOverride = { fromTier, toTier, basis, agendaQuote, evidenceQuote, evidenceId, model, at }, rendered with an AI badge, the from->to arrow and both quotes inline, plus "undo to <deterministic tier>". Undo writes status='dismissed', and a dismissed override for the same (meetingId, userId, basis) is never re-applied on any subsequent run of any surface — that is what stops the model re-arguing a point the organizer already settled every time the panel reopens. Dismissal rate on required rows is the instrument: above roughly 30% the weights are wrong, not the organizers.

### Reason text

Every reason is a stored { code, points, evidence: { ids }, en, si } record. `en` and `si` are TEMPLATES filled from queried values — never model-authored prose, except the two ai_* codes whose quoted spans are validated verbatim substrings. Sinhala strings sit in the same pure template table and are tested the same way: this team's own meeting notes already ship bilingual output (meetingAiNotes.terms exists to give short සිංහල explanations), and the harshest lines are the ones most likely to be misread in a second language. One extra column, cheapest mitigation on the list.

HARD CONSTRAINT, enforced by a lint test over the template table: every line contains a NUMBER, a PROPER NOUN, or a DATE. Banned outright: "seems relevant", "often contributes", "likely needed", "key stakeholder", "high engagement", "usually attends", and every confidence adjective.

Shipped templates (organizer view):
- followup_pinned "Pinned to this meeting: 'Send the Vela staging credentials' — added by Nuwan on 4 Aug."
- followup_open "Owes 2 open items from Vela Weekly (28 Jul): 'confirm the SLA wording', 'check the invoice export'."
- followup_answered_here (retro) "Answered 3 open items in this meeting."
- followup_redacted "2 open items from meetings you can't see." (count only — never titles)
- task_open "Owns 3 open tasks in Vela, 2 in progress."
- task_sprint "2 of their open Vela tasks are in Sprint 12 (ends 19 Aug)."
- role_topic "Agenda says 'the new checkout flow mockups'; their role is UI/UX Designer."
- discussed "Named in the AI notes of 2 past Vela Weekly meetings (4 discussion points)."
- spoke "Took 9 of 31 attributed speaking turns across the last 3 recorded Vela Weekly meetings."
- lead "Lead of Vela."
- allocated "Assigned to Vela at 60%." (always rendered last and de-emphasised — it is the weakest line in the system and should read that way)
- attended "Attended 5 of the last 6 Vela Weekly meetings."
- agenda_match "Agenda line 'migrate the invoice export' matches their open task 'fix invoice export CSV'."
- organizer "Organizer."
- opted_in "Asked to be included in this series."
- conflict (flag, organizer only) "Already on 'Client demo — Orbit', 14:00-15:00."
Caveat lines, always shown when they apply, never collapsed: inferred_app, ai_unavailable, thin_evidence, no_series ("Only 1 earlier 'Vela Weekly' — series signals unavailable"), new_person ("Joined Vela 6 days ago — history signals unavailable"), speaker_unresolved ("2 of 3 recordings have unassigned speakers — participation not counted").

DISPLAY: the organizer sees the top 3 positive lines ordered by points contributed, plus every caveat, plus the score as a number with its threshold ("41 — required at 30+"), plus a "why?" disclosure holding the full ledger. Everyone else — including the person themselves — sees the tier and positive reasons only, no number, no ledger, no "not recommended" list. There is no negative reason template anywhere in this model, because there is no negative term.

Two lines are deliberately NOT shipped. "No open items, no tasks in Vela, and no recording of this series naming them" — "no evidence" is a statement about LogPup's data, so it is attached to the RUN ("LogPup has nothing on file for this meeting"), never to a named person. And "matched by name — not linked to their account" is never shown as a reason about a person; unlinked follow-ups surface once, to admins, as a data-quality item ("3 follow-ups on Vela could not be linked to an account").

The skipper recap (the decided skip payoff) NEVER states or implies a tier and never includes any reasons content. It goes to every non-attendee on the app — not only to people the model skipped, and including people who declined — so receiving it carries no information about how the model rated you: "Vela discussed the refund flow on Tuesday — here's what came out of it."

### Degradation

COLD START (the modal case for at least the next six weeks, and the state to design for first). No transcripts, no meeting_ai_notes, no accumulated follow-ups: E4/E5/E7 are UNAVAILABLE and contribute 0 with a caveat line, never a zero-as-judgement. With fewer than 2 candidates carrying hard evidence the model enters ABSTAIN MODE: no tiers written, no negative statement about anyone, organizer pre-filled required, everyone eligible and assigned to the app pre-filled OPTIONAL, header "Not enough to go on yet — everyone on Vela is pre-filled as optional; trim it yourself." Because thresholds are absolute and there is no denominator, thin data produces fewer `required` rows rather than a confidently re-scaled ranking. The whole assignment-history / as-of allocation family is cut outright (see rejected), so there is no silent-zeros failure to guard.

NO appId. Ladder, highest confidence first, stopping at the first hit and recording which rung fired: (0) organizer, always available; (1) app implied by the CURRENT human-committed attendee set, weighted by allocationPct, ABSTAINING when the top two are within 1.5x — gated off on the scheduling surface, where inferring from attendees the recommender itself pre-filled is circular; (2) apps of tasks this meeting produced via meetingTaskSuggestions.createdTaskId -> tasks.appId (retro only, tasks.appId is NOT NULL so it is clean when it fires); (3) series siblings sharing seriesKey that DO carry an appId; (4) title/agenda vs apps.name/slug/techTags, using matchApp extracted from meeting-form.tsx:86 to src/lib/app-match.ts with a sibling .test.ts. An inferred app powers E2/E3/E6 at x0.6 with every reason prefixed "inferred:", and is NEVER written back to meetings.appId. Nothing inferrable -> APP-LESS MODE: only E1, E4, E5, E7 and A1 are available, the R8 ceiling applies (nobody required except the organizer, a pinned-followup holder, or a series regular at >=0.75 over >=3 occurrences), and the panel says "No app on this meeting — ranked on open items and the standing invite list only." Note that appId null is indistinguishable from "its app was deleted" (onDelete set null), and a deleted app also cascades away its assignment_history, so that case is unrecoverable by design.

NO TRANSCRIPTS / UNRESOLVED SPEAKERS. E5 is per-candidate: a past meeting counts only if that specific person has a meeting_speakers mapping or a segment carrying their speakerId. Everything else — unmapped "Speaker 3", the giant single unattributed segment both prompts instruct the model to emit when it cannot diarize, two people named Kasun that matchPersonToAttendee deliberately refuses to guess between — is UNAVAILABLE, contributing nothing. There is no path in this model by which absent attribution becomes "they were silent", because there is no negative term to reach.

TINY TEAM. Pool <= 4: `skip` is disabled entirely, every pool member is at least optional, and only the organizer and pinned-followup holders can be required unless someone clears 30 deterministic points. A recommender that excludes people from a four-person meeting is answering a question nobody asked. More generally, the R5 floors mean anyone assigned to the meeting's app is at least optional at any team size — `skip` is reserved for people pulled into the pool by stale attendance or by tasks in an app they are not on.

NO AGENDA. E3 falls back to title tokens and contributes 0 if the title has fewer than 3 non-stopword words; A1 is not called at all and contributes 0. Thresholds do not move.

AI UNAVAILABLE. A1 = 0, reason ai_unavailable, deterministic result ships unchanged. The feature is complete without Gemini ever being reachable.

RETROSPECTIVE. Pool = evidence pool UNION actual attendees (eligibility gate suppressed for the second set). Follow-ups reconstructed as-of (status='open' OR resolvedAt > meeting.startsAt), with items resolvedInMeetingId = this meeting scored x1.25 because being answered in the room proves the person was needed. Tasks filtered to createdAt <= meeting.startsAt and capped at 10, because open-at-the-time is genuinely underivable without a tasks.updatedAt column. Allocation and lead are today's values, labelled "Allocation and lead shown are today's — LogPup keeps no history of either at meeting time." Nobody who attended is tiered skip. Output is organizer-private, split into "invited, could have been optional" and "not invited, had evidence", stores no per-person negative reason, and is pruned after 180 days.

### Rejected (scoring)

- SPEAKING-SHARE NEGATIVE BRANCH (both designs' -12 / -10 plus a permanent tier cap). Cut entirely; E5 is positive-only, capped at 8. It is the single most dangerous term in the candidate designs: the per-meeting diarization gate validates the MEETING, not the candidate, so an attendee whose label stayed 'Speaker 3' scores share 0.00 and is judged silent — contradicting the rule both designs write down. It punishes the quiet senior who unblocks two people by listening, and it is the term that most cleanly launders medical leave, parental leave and the Avurudu shutdown as disengagement, in a schema with no absence table at all.

- CHARACTER-COUNT AS SPEAKING VOLUME. Replaced with turn count. The transcription prompt treats Sinhala/English code-switching as this team's common case, and the same utterance renders ~25-30% shorter in Sinhala script — a char-based share credits English-medium schooling, not contribution, and at the band boundaries that is a decisive 7-point swing.

- SELF-REINFORCING SILENCE LOOP (being tiered optional, not attending, then being scored as silent next run). Structurally impossible now that E5 cannot go negative, so the exclusion rule the critique proposed is unnecessary. The residual loop — attendance feeding E7 — is capped at 6/100 and barred from creating required.

- RSVP DECLINE PENALTY (-8 / -6). Cut. The column defaults to 'pending' and exactly one control in the entire app writes it (the button group inside a meeting-list row), so it will be inert for months; it is confounded with leave and illness; and it is a one-way ratchet in a product where accepting is deliberately worth nothing. Cutting it removes the need for the whole 'answered >= 3' gate. Replaced with a positive, person-controlled 'Ask to be included' opt-in that floors the person at optional on that series and outranks the model — the only lever in either candidate design that a person could pull in their own favour.

- AS-OF ALLOCATION AND AS-OF TOTAL LOAD via assignment_history (both designs' retrospective allocation). Cut entirely, along with the reach guard, the timestamptz-vs-timestamp boundary problem and the tombstone rule. The table is one day old, every pre-existing row is backfilled with effective_from = GREATEST(user.created_at, app.created_at) — an admitted lower bound — and, as the critique correctly found, min(effective_from) is therefore the org's founding date, so the guard both designs specified passes for every meeting ever and prints today's allocation as verified history with the caveat suppressed. Retro uses today's allocation with a visible label instead. Revisit in six weeks when observed rows exist; the correct guard then is min(created_at) evaluated per (userId, appId), not min(effective_from) globally.

- OVER-ALLOCATION PENALTY (totalPct > 100 -> -4 / -8 / -14). Cut. allocationPct is a workload share, not a calendar — there is no free/busy, no working hours, no leave table — so a 130% person may be entirely free at 3pm. It also silently includes allocation to paused and archived apps. Real double-booking is derivable and is surfaced as an organizer-facing flag instead, with no effect on the score.

- DUE-DATE AND OVERDUE TASK TERMS. Cut. dueDate is only ever set by five natural-language phrase families in the quick-add or by a Gemini guess, taskUpdateInput has no dueDate key so it can never be edited or cleared, the board does not render due dates at all so the organizer cannot click through and verify the claim, and Gemini-guessed dates therefore accumulate as permanent false overdues on people who never agreed to them. Ship the board's due-date UI first; revisit when per-app coverage is measurable.

- PER-PERSON WEEKLY REQUIRED BUDGET (Brake 2). Cut. Calibrated for a corporate calendar: a daily standup alone eats 5 of 6 slots, so it demotes the app lead on Wednesday's incident review for his own app, it picks its victim by run order rather than by any property of the meeting, and it publishes a reason implying the person is the constraint. Replaced by the R10 soft cap: a private warning to the organizer above 8 required, with no automatic demotion.

- MULTI-APP LEAD DILUTION (Brake 3, lead of >=4 apps -> lead signal halved). Cut. In a single-digit studio one person genuinely leading most of the portfolio is the org chart, not signal inflation, and it made the denominator differ between candidates in the same meeting so the numbers shown side by side were not comparable. The absolute ledger has no denominator, and E6 is capped at 12/100 anyway.

- PER-MEETING REQUIRED-COUNT CAP (Brake 4, max(3, ceil(0.5*pool))). Cut. In this studio it always evaluates to 3, it demoted the designer at sprint planning with 'ranked 4th', and it broke ties on allocationPct — giving the model's already-dominant admin-typed field a second vote. A meeting that genuinely needs four people is routine here.

- NORMALIZED SCORE WITH DYNAMIC THRESHOLDS (both designs, in different forms). Cut in favour of an absolute 100-point ledger. Design B's denominator can be legitimately zero (no app + short title + no agenda + no series history = the first meeting anyone creates), producing NaN, and NaN fails every >= comparison, so every candidate silently became skip — no invite, no notification, no error. Design A's attainable credited 30 unearnable points whenever appId merely resolved, inflating the cuts and pushing thin runs past its own thin-evidence guard, and it was computed globally while family availability is per-candidate. Absolute points also preserve the distinction the feature exists on: zero means no evidence, not lowest-ranked.

- AI DOWNWARD OVERRIDE (Design B allowed required->optional and optional->skip). Cut. The evidence is a substring of agenda text written by a user and fed to the model in the same turn as the instructions; a wrong demotion is silent and unrecoverable; and there is nothing in the ledger for a demotion to argue against, since no term is negative. The AI moves up one step, at most twice, or not at all.

- DRAFT PERSISTENCE ON THE SCHEDULING SURFACE. Not built. There is no meetings row while the form is open, meeting_attendee_recommendations keys on meetingId, and a nullable-meetingId + draftKey + partial-unique-index scheme is real schema cost for a surface whose state is the form itself. The scheduling surface is therefore declared explicitly STATELESS — no persistence, no dismissal memory, no weekly accounting — and the run snapshot is persisted at createMeeting time with surface='schedule'. Stated rather than silently assumed, because both candidate designs presented the four surfaces as interchangeable when one of them cannot write a row.

- VIEWER-SCOPED FOLLOW-UP READ (Design A reused fetchCarriedFollowups' caller-entitlement clause). Cut. It made a person's publicly visible tier a function of who last opened the panel, and a member reopening after an admin would silently UPSERT a demotion. The scorer reads with full visibility and the UI redacts to a bare count; an upsert guard additionally refuses any write whose hard-evidence count for that candidate is lower than the stored one.

- PUBLISHING SCORES AND REASONS TO EVERYONE. Cut. getMeetingsForApp filters on appId alone, so anything rendered on a meeting page is readable by everyone on the app. Scores, the full ledger, the 'not recommended' list and all retrospective output are organizer-and-admin only.

- THE 'no evidence' AND 'not linked to their account' REASON LINES. Cut as statements about a named person. The first is a fact about LogPup's data and is attached to the run; the second is a data-quality item shown once to admins.

- ROLE FLOOR SET AT 'optional' ONLY (Design B's rule 4 shape for the role-topic case). Rejected as insufficient. A deterministic PRIMARY role/topic match on someone assigned to the app floors at REQUIRED, because the failure it prevents — the designer optional at her own design review, the QA engineer skipped at the incident review — is the model's worst and most predictable error, and the floor cites a verbatim agenda span plus a verbatim role string, making it exactly as auditable as any other reason.

- TASK RECENCY / MOMENTUM, and retrospective open-at-the-time task state. Not derivable: tasks has createdAt but no updatedAt and no completion timestamp, so a task dragged to in_progress this morning is indistinguishable from one sitting there since March. The +2 in_progress term is the best available proxy and is weak. Accepted as a gap rather than faked; see open_questions for the schema decision.

- LEAD-AS-OF for the retrospective surface. Not derivable and not back-derivable: updateApp overwrites apps.leadId in place with no history row. Retro uses today's lead with a visible label; E6's 12-point cap keeps the imprecision cheap.
