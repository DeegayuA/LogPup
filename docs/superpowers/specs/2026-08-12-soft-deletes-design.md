# App-wide Soft Deletes — Design Spec (sub-project D)

Date: 2026-08-12
Status: designed under "do all tasks" mandate; user requirement verbatim: "no permenet delete (unless admin db clear), use all things as soft deletes, if need admin can see what delete, who delete, when, also can get it back". Delegated decisions under Assumptions — veto by editing this file.
Suite order: **D (this spec, built FIRST)** → A attendee recommender → B meeting load → C people KPIs.

## One flagged exception requiring your attention

**Gemini API keys stay hard-delete.** A credential is a secret, not data: soft-deleting it would keep decryptable ciphertext indefinitely, strip the owner of the power to erase their own secret, and leak key metadata to admins. Same reasoning backup.ts already uses to exclude keys from backups. Veto here if you want keys in the trash too.


## Mechanism

FINAL: Design 1 (per-table flag columns + guarded live views), hardened against every critique finding. Rationale for rejecting the tombstone design is in `rejected`. Add two columns to each of FIVE soft tables in src/db/schema.ts: `deletedAt: timestamp('deleted_at', { withTimezone: true })` (NULL = live) and `deletedBy: uuid('deleted_by').references(() => users.id)` with no onDelete action (safe: users are deactivate-only — the same reasoning schema.ts records for activity_log.actorId). Soft delete = `db.update(T).set({ deletedAt: new Date(), deletedBy: session.user.id }).where(and(eq(T.id, id), isNull(T.deletedAt)))` — the isNull guard makes a concurrent double-delete a 0-row typed no-op; single UPDATE, so no atomicity machinery needed on neon-http. Restore = the inverse UPDATE guarded by `isNotNull(deletedAt)`. Purge keeps the real db.delete bodies (the schema's untouched onDelete cascade/set-null clauses become purge machinery, not dead code) in an admin-only trash-actions module, ordered race-safely (see external_cleanup). New module src/db/live.ts: connection-free subqueries built with `new QueryBuilder()` from 'drizzle-orm/pg-core' (drizzle 0.45.2 supports subquery objects in from() and all join positions; Postgres inlines them so existing indexes still apply; NEVER module-scope db.select() — the lazy db Proxy in src/db/index.ts would crash next build without DATABASE_URL). Exports: liveMeetings, liveTasks, liveSprints, liveNoteSegments, liveScreenshots — PLUS per-table alias factories `liveTasksAs(name)`, `liveMeetingsAs(name)`, etc. (a fresh QueryBuilder subquery per call, because a fixed subquery object cannot be aliased or reused twice in one statement — this closes the alias() evasion found at ai-actions.ts:1992) — plus a SOFT_TABLES map (raw table, live view, SQL name, alias factory) and a MEETING_CHILD_TABLES list, the single sources of truth the enforcement test iterates. Migration: hand-write drizzle/0022_soft_delete.sql (5 tables x 2 nullable ADD COLUMN — zero backfill/downtime; plus partial-index hardening: recreate tasks_app_sprint_sort_idx and add meetings(starts_at) index, both WHERE deleted_at IS NULL) and apply via the same manual path used for drizzle/0021_activity_log.sql, since npm run db:migrate is broken repo-wide (memory: logpup-migrations-untracked). D adds NO new tables, so neither clearTestData's delete list nor backup.ts's enumeration changes — and because gemini keys stay hard-deleted (see tables), no credential ciphertext ever enters trash or backups. Verified against current main: logActivity is already wired into all six delete-path action files by the parallel session (deleteMeeting now at meetings/actions.ts:492-538 with logActivity at :538) — D edits on top of those calls and preserves them, changing the verb payloads to 'deleted'/'restored'/'purged'.

## Cascade rule

MEETINGS — parent-only mark, single UPDATE, zero child writes; the 8-table cascade never fires so restore is trivially lossless. Children stay invisible because (a) every detail/gate path loads the meeting through liveMeetings first — getMeetingIntel, getMeetingNoteTimeline, canReadMeetingIntel, BOTH canManageMeeting variants (sync in meetings/actions.ts, async in ai-actions.ts) — so a trashed meeting 404s and cannot be mutated through its gates; and (b) every list/join path targets liveMeetings (dashboard upcoming card, getPersonMeetings, getPersonFollowups, followup carry-forward, search). The predicate lives INSIDE the subquery, so leftJoin(liveMeetings) NULLs a trashed meeting exactly as the hard cascade used to — no ON-clause-vs-WHERE trap; every documented leftJoin justification stands unchanged. Notifications (cascade no longer fires): listNotifications and unreadNotificationCount add leftJoin(liveMeetings) with `(notifications.meetingId IS NULL OR liveMeetings.id IS NOT NULL)` — hidden while trashed, back on restore (unread count may rise again — accepted), dead by real cascade at purge. THE CHILD-TABLE INVARIANT IS CI-ENFORCED, NOT CONVENTION (fixes the D1 blocker): live.test.ts treats the 9 child tables as join-required — any read-form use (.from, joins, alias()) of a child table must co-occur with liveMeetings/liveMeetingsAs in the same statement or be explicitly allowlisted; a future sub-project A co-attendance self-join on meeting_attendees alone, or a transcript search over meeting_recording_segments, fails CI until it names its liveness source. SPRINTS — deliberately no cascade to tasks: sprintId is never nulled (SET NULL never fires), making restore lossless. The trashed-sprint visibility rule is defined ONCE as an exported pure builder (new src/features/sprints/backlog.ts): backlog = liveTasks leftJoin liveSprints where liveSprints.id IS NULL — covering truly-unassigned tasks and tasks of trashed sprints. Both existing `isNull(tasks.sprintId)` spellings (sprints/queries.ts:176, task-actions.ts:230 — verified) are converted to the builder, and the test forbids `isNull(` adjacent to `.sprintId` outside that module (fixes the split-predicate major: no task can vanish from every surface). Sprint selector, roadmap, getActiveSprints read liveSprints; bulkUpdateTasks validates target sprint against liveSprints and permitted rows against liveTasks. deleteSprint still returns releasedTasks (live count) — toast now means 'tasks temporarily showing in backlog'. If a user explicitly moves a ghost-backlog task while the sprint is trashed, that write wins and restore respects it — explicit moves are never yanked back (the sprint-repointing pathology of the tombstone design cannot occur because nothing is ever re-pointed). TASKS/SEGMENTS/KEYFRAMES — leaf marks; the suggestion SET NULLs stop firing so accepted-suggestion provenance survives trash+restore (strictly better than today). FUTURE PARENTS (app delete, if ever added): born soft — batch-mark all children in one db.batch stamping the parent's exact deletedAt Date on every child; restore clears only children WHERE deleted_at = parent's stamp, so independently-earlier-trashed children stay trashed. Specified now so A/B/C inherit it.

## Restore rule

Restore is ADMIN-ONLY (requireAdmin) for every entity — matching the verbatim requirement; stated consequence in the spec: a member who trashes their own meeting asks an admin (a decision, not a bug). Actions live in features/admin/trash-actions.ts, return typed ActionResult, call the existing revalidate helpers, and logActivity('restored'). Mechanics: UPDATE set deletedAt=NULL, deletedBy=NULL WHERE id=? AND deletedAt IS NOT NULL — a purged or already-restored row yields 0 rows and a typed error, and because purge's row-delete runs FIRST under the same isNotNull guard (see external_cleanup), the restore-vs-purge race always has exactly one winner and can never produce a live meeting with deleted blobs. CONFLICT RULES: (1) Unique keys — none of the 5 soft tables carries a user-facing unique index today, so no partial-unique migration now; the pattern is specified for the future (any unique index spanning a soft table becomes partial WHERE deleted_at IS NULL; restore preflights the live competitor and fails typed, naming it). (2) Keyframe restore preflights `live count + 1 <= MAX_KEYFRAMES_PER_MEETING` and fails typed ('meeting is at its keyframe cap — remove a live frame first') — closes the cap-bypass loop; the cap itself counts LIVE frames only, client and server. (3) Child under a trashed parent — an individually-trashed segment/keyframe whose meeting is trashed cannot be restored; the UI disables the button with 'restore the meeting first'. Restoring the meeting does NOT auto-restore individually-trashed children (they were removed by separate intent). (4) Task restored while its sprint is trashed lands visible in backlog via the join rule and snaps back when the sprint is restored; task restored after its sprint was PURGED restores with sprintId already NULL (purge fired the real SET NULL on all rows including trashed ones) — consistent, order-independent. (5) Meeting restored under an archived app: appId was never nulled, renders normally (archived apps still render). (6) Calendar: restore does NOT auto-recreate the Google event (fixes the impersonation major — an admin must never mint invites and outbound email under the creator's OAuth identity, nor surprise external guests who received a cancellation). Restore nulls the stale googleEventId, succeeds, and the ActionResult carries 'calendar invite was cancelled and not resent'; the creator can re-share via the existing tokenless ICS route. (7) Assignments — restore is NOT an un-mark: restoreAssignment is a guarded db.batch mirroring createAssignment (insert the assignments row, failing typed if the (user, app) pair is already live; close the open 'removed' tombstone; open a new 'assigned' interval), preserving the one-open-interval invariant with the same per-statement guards as removeAssignment.

## Query safety

The heart, per the repo's own enforce-don't-document precedent (the schema.ts:81-110 burn scar; the partial-index-instead-of-comment pattern). LAYER 1 — STRUCTURAL: every live read consumes liveX/liveXAs from src/db/live.ts; the deletedAt-IS-NULL predicate exists in exactly ONE expression per table in the codebase. Authors cannot forget the filter because the imported object already contains it; leftJoin semantics are automatically correct because the predicate is inside the subquery. The silent-wrong-number aggregate class dies the same way: listApps/getAppCounts countWhere sources, getActiveSprints counts, getPersonActivity graph, unreadNotificationCount all route through live views. The one genuine choke point (meetingColumns + attachAttendees) is rebuilt over liveMeetings, converting all three meeting list reads at once. LAYER 2 — ENFORCEMENT TEST, src/db/live.test.ts (pure vitest, no DB), iterating SOFT_TABLES and MEETING_CHILD_TABLES so identifiers are never hand-kept. It scans src/**/*.ts and fails on: (a) read-form use of the 5 raw soft tables — `.from(raw)`, `.innerJoin(raw`, `.leftJoin(raw` — outside the allowlist; (b) `alias(<softTable>` anywhere outside src/db/live.ts (closes the evasion the existing ai-actions.ts:1992 `alias(tasks, ...)` proves is live code today — that site converts to liveTasksAs); (c) read-form use OR alias of any of the 9 meeting-child tables in a statement that does not also reference liveMeetings/liveMeetingsAs, unless allowlisted — the child-table blocker becomes CI, not convention, and sub-project A/B/C queries inherit the guard the day they are written; (d) `db.delete(<softTable>)` anywhere outside admin/actions.ts and trash-actions.ts — 'no permanent delete' as a failing test; (e) any schema table bearing a deletedAt column missing from SOFT_TABLES — the next soft table cannot skip the guard; (f) `isNull(` adjacent to `.sprintId` outside sprints/backlog.ts — the backlog rule stays single-sourced. Allowlist (explicit, in the test file): src/db/live.ts, features/admin/trash-queries.ts, trash-actions.ts, backup.ts (backups must include trash), admin/actions.ts (the clear), the meeting-keyframes proxy route, and the commented legacy-notes EXISTS probe. WRITE SIDE: updates must target raw tables (subqueries aren't update targets), so write liveness is load-then-check routed through liveX at the dangerous sites — bulkUpdateTasks permitted-rows + target-sprint, keyframe cap count, both canManageMeeting gates — and the residual (an UPDATE landing on a trashed row) is invisible-but-harmless since all reads filter. HONEST LIMIT, stated in the spec: the guarantee is repo-level, not DB-level (raw psql sees trashed rows) — accepted for a 9-person internal tool; the test's failures also serve as the one-time conversion worklist (~25-30 sites including the inline ai-actions.ts reads), so the audit is mechanical, land-test-first, convert until green.

## External cleanup (Blob / Google Calendar / notifications)

GOOGLE CALENDAR: event delete stays AT soft-delete time (guests must stop seeing the invite), best-effort with the creator's refresh token exactly as today; googleEventId is kept on the trashed row for audit. Restore: NO auto-recreate (see restore_rule) — googleEventId nulled, warning in the ActionResult, ICS route covers re-inviting. Purge: no calendar work. VERCEL BLOB (keyframes): NO del() at soft-delete time — deleteMeetingKeyframe loses its del() call and deleteMeeting loses its pre-delete sweep; blobPathname is preserved so the filmstrip restores intact. All blob deletion moves to purge with RACE-SAFE ORDERING (fixes the purge-vs-restore major): purgeMeeting = (1) SELECT all meeting_screenshots pathnames incl. trashed (raw, allowlisted) into memory, (2) `db.delete(meetings).where(and(eq(id), isNotNull(deletedAt)))` — if 0 rows (concurrently restored), STOP, no blobs touched; a live meeting can never be hard-deleted or lose its blobs through trash housekeeping, (3) best-effort del() each pathname — a crash between (2) and (3) orphans blobs, the already-accepted posture, strictly safer than the reverse order. purgeKeyframe/purgeSegment/purgeTask/purgeSprint use the same isNotNull-guarded delete-first shape. PURGE GATE: admin + typed confirm, NO ENABLE_DB_CLEAR requirement, every purge logged via logActivity('purged') with metadata — decided deliberately: the deletion-as-redaction gap (a sensitive keyframe/segment must have a completion path in a deployment where the clear flag is off) outweighs the minor fence-widening, and the audit row keeps destruction accountable. Listed under assumptions for veto. KEYFRAME PROXY (route not yet in tree — parallel session): its authorization is SPECIFIED in D, not inherited from the avatar pattern: resolve pathname → meeting_screenshots row → require frame live AND meeting live for non-admins (404 otherwise), admin bypass for trash preview; the route is on the test allowlist so its raw lookup is legal; manual checklist asserts a previously-working keyframe URL 404s after trashing, including via the PWA cache. GEMINI KEYS: hard delete unchanged — no ciphertext in trash, no backup contamination, backup.ts's secret-exclusion contract untouched. BACKUPS: buildSnapshot's full-table selects pick up the two new columns automatically, so backups include trashed rows (required for 'admin can get it back'); no enumeration change. clearTestData: unchanged, purges trash for free via unconditional deletes — recorded in the spec so nobody adds a deletedAt predicate to 'fix' it.

## Rejected

- Tombstone/deleted_items design (Design 2) as the mechanism — rejected despite its genuine query-safety elegance: (1) its atomicity story was found wrong (data-modifying CTEs execute exactly once even when the outer DELETE loses a race, committing duplicate tombstones whose later purge destroys a LIVE meeting's blobs); (2) restore is re-insertion into a moved-on schema, an ongoing codec/upcaster tax with fail-closed dead ends; (3) jsonb payloads are invisible to privacy-erasure prunes — its own completeness test would MANDATE snapshotting sub-project A's recommendation rows past their 180-day erasure deadline; (4) full-table deleted_items backup smuggles gemini ciphertext into backups against backup.ts's explicit contract; (5) sprint-restore effect re-pointing is an approximation that yanks deliberately-triaged tasks back. The flag design fixes its own critiques with test extensions; the tombstone design's flaws require redesigning its core.

- SQL views (DB-level live views) — zero benefit over inlined QueryBuilder subqueries at this scale, and every view is another object the broken migration flow must create.

- Per-child deletedAt columns on the 9 meeting child tables — 18 columns and a multi-statement non-atomic cascade-mark on every meeting delete, versus one UPDATE + a CI-enforced join rule.

- Soft-deleting assignments rows — would break assignments_user_app_idx, violate the schema-documented no-new-filter invariant, and duplicate a working tombstone system.

- Soft-deleting gemini keys (both drafts proposed it) — indefinite credential retention is a liability, not a feature; owner-initiated revocation must physically destroy ciphertext.

- Auto-recreating the Google Calendar event on restore — mints invites and outbound email under the creator's OAuth identity on an action an admin took, and re-invites external guests who received a cancellation.

- Mandatory TTL auto-purge for content-bearing leaves — contradicts the verbatim keep-forever requirement; the redaction completion path is instead the ungated admin purge (see assumptions), accepted residual: the deleter must involve an admin.

- Per-author restore notifications and a member-visible 'your deleted items' view — YAGNI at 9 people; the member-visible activity feed already shows 'restored' rows; revisit on request.

- Gating per-item purge behind ENABLE_DB_CLEAR — would leave production (flag off) with NO path to complete a redaction of a sensitive keyframe; rejected in favor of admin + typed confirm + audit log.

- A trash retention/TTL knob — trash grows unbounded until purge; negligible at studio scale, surface bounded by LIMIT 50; revisit if it matters.

## Assumptions (delegated decisions — veto here)

- Gemini API keys STAY HARD-DELETED (overrides the literal 'use all things as soft deletes'): a credential is a secret, not restorable data — mirrors backup.ts's own exclusion of geminiKeys. Veto = keys go soft with owner-visible trash + mandatory short TTL purge + no admin restore.

- Restore and trash visibility are ADMIN-ONLY; a member who trashes their own meeting cannot self-restore (reading of the verbatim 'admin can see... can get it back'). Veto = add self-restore for own items.

- Per-item 'Delete forever' (purge) requires admin + typed confirm but NOT ENABLE_DB_CLEAR, and every purge is activity-logged — chosen so a redaction (sensitive keyframe/segment) can be completed in production where the clear flag is off. Veto = env-gate purge; consequence: no permanent deletion path in prod at all.

- Restore does NOT resend the Google Calendar invite; the creator re-shares via the existing ICS route. Veto = add a creator-facing 'resend invite' button (their token, their click) — never admin-triggered.

- Content-bearing leaves (keyframes, note segments) are retained in trash indefinitely with no TTL, visible/previewable to admins only, with neutral labels in trash and the activity feed — the deleter must ask an admin to complete a true erasure. Accepted per the keep-forever requirement.

- Delete-confirmation copy changes app-wide to 'Moves to Trash — admins can view and restore it' — the contract change is disclosed to members, not silent.

- Trashed meetings hide (not delete) their notifications; unread counts can rise again on restore.
